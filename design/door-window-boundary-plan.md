## 0. 结论速览

用户两条反馈各对应**一个正确性缺陷**和**一组口径不一致**。反馈②（贴墙看穿）是**单一算术缺陷**（射线从不检测起点格），
离线模型里可 100% 复现；反馈①（门/窗边界不平滑）是**六条互相独立的机制叠加**，按对玩家观感的贡献排序如下。

**一句话结论**：墙之所以"平滑"，是因为它的 alpha 来自**原生 40px 角点场（1 样本/瓦片）+ 双线性放大 + 原生时间迟滞（只升不降的棘轮）**，
是一条低通、连续、有记忆的场；而门/窗所在的区域被拆成"透光叶面（被提升为全可见）"+"门后平顶（单值）"+"记忆/未探索（两值）"
三段互不连续的口径，交界全部落在 40px 瓦片边界上。贴墙漏视则是**射线起点格豁免**这一条算术缺陷：
站立时眼点始终在身体盒内（安全），但**坐姿**把盒子高度砍半、让玩家能再贴近墙 35px，眼点就落进墙瓦片，整面墙随即失效。

## 1. 问题与口径

### 1.1 用户反馈（2026-11-04）

1. **"现在由可透光门和窗户提供的视野边界远不如墙造成的视野边界平滑。"**
   —— 注意这是"**边界**（boundary）"而非"亮度"：玩家看的是"能看见 / 看不见"那条线的**形状与过渡**。
2. **"玩家角色贴墙过近时可能获得墙后视野。"**
   —— "**可能**"是关键线索：它取决于朝向与接触状态，而不是恒定的。

两条反馈都发生在 **current 模式**（真实线状阴影）下；`classic` 模式走的是另一套（复刻原版）路径，本方案不涉及。

## 3. current 模式的现状机制还原

### 3.1 一帧的完整链路（带行号）

```
onFrameInner (1037)
 ├ updateViewDistances (1088)               locDist1/2、curBlur = soft*fogSub/40 (:738)
 ├ playerVisionEye (1094 → 1767)            取 vis.osn.body.head.morda.eye 的世界坐标；失败回落 (gg.X, gg.Y-gg.scY*0.75)
 ├ prepareOcclusion (1096 → 1730)           把每格 tileOpac 快照进 rayOpac（门开闭/水即时生效）
 ├ moved = |eye-last|>cfgMotionStep          (1095, 阈值 4.0px)
 └ needFov = moved || opacityChanged || structHash 变化 || frameCount%90==0   (1100-1101)
      → computeFov (1788)                   瓦片中心一次 castRay → fov[] ∈ {VISIBLE, DIM, NONE}
        ├ 半径框内逐瓦片：lit>=litmin → VISIBLE+explored；lit>0 → DIM+explored；否则 NONE   (1839-1852)
        └ 墙可见性传播：opac>0 的瓦片，只要 8 邻有"可见且 opac<=0"的瓦片 → 强制 VISIBLE  (1859-1894)
      → applyVision (2109)
        └ fillFogCache (2267)               逐瓦片四分支（见 3.2）
            ├ t.opac >= 1        → fillWallTile(tx,ty)          （原生角点双线性, :2709）
            ├ f == FOV_DIM       → recalcTile(...,doorF,true)   （门景平顶, :2398 传 :2311）
            ├ f==VISIBLE && cLit==4 → fillLitTile               （整瓦纯距离衰减, :2469）
            ├ cLit==0 && (f!=VISIBLE || (flags&240)==0) → fillMemoryTile(dimA)  （整瓦记忆/黑）
            └ 其它               → recalcTile(...,dimF,false)   （子格射线）
        └ applyFilter(fogRaw → fogBmp, curBlur)  （:2256）
```

关键：**`fov[]` 是瓦片级（40px）三态**，而 `fillFogCache` 内部又有**子格级（10px）**计算。
两套粒度混用是 R4 的来源；三套 alpha 公式混用是 R2 的来源。

### 3.2 三套 alpha 口径并存（这是"不平滑"的结构性原因）

| 区域 | 走哪个分支 | alpha 公式 | 采样粒度 | 亮度来源 |
|---|---|---|---|---|
| **墙**（`opac>=1`） | `fillWallTile` | `a = round(255 - (255-gameA)*(1-cur+cur*dim))`，四角**双线性** | **40px 角点**（1 样本/瓦片） | 原生 `Tile.visi` 角点场（`explorationLight:300-309`） |
| **门**（累计透光后 `0<lit<litmin`） | `recalcTile(doorView=true)` | `br = max(lit×falloff, **doordim**)`；`a=round((1-br)*255)` | 10px 子格 | RV 自己的 DDA 射线 |
| **窗/栅格/开口**（`lit>=litmin`） | `fillLitTile` / `recalcTile(dimF)` | `br = max(lit×falloff, **dim**)`；`fillLitTile` 里 **`lit` 因子被丢掉** | 10px 子格 | RV 自己的 DDA 射线 |
| **记忆/未探索** | `fillMemoryTile` | 曾见 → `dimA = round((1-dim)*255)`；未见 → 255 | 10px 子格 | `seenSub`/`fullySeen` |

三条公式在"记忆/未探索"处汇合（都是 `dimA`），但在**门后**与**门叶**两处各自突变：

- 门后：`doordim`（=0.85，alpha 38）**比记忆区 `dim`（=0.6，alpha 102）更亮**，两者相差 **64 级 alpha**；
- 门/窗叶：被传播提升为 VISIBLE 后按"地板衰减"或 `fillLitTile` 画，几乎无雾（模型实测 alpha 16–29），
  与紧邻墙（20–223 的连续梯度）**在 40px 瓦片线上直接断开**。

### 3.3 墙为什么"平滑"？—— 三层平滑叠加

1. **空间低通**：原生 `lightBmp` 是"**每瓦片角 1 个样本**"（`Location.as:3162/3238` 用 `setPixel32(x, y+1, …)` 写 1px/角），
   显示时被放大 40 倍做双线性插值 ⇒ 墙面的亮度是**40px 网格上的分段线性函数**，天然没有 10px 级台阶。
2. **时间迟滞**：`Tile.updVisi()`（`Tile.as:271-279`）每帧只把 `visi` 向 `t_visi` 靠 **+0.1**；
   `retDark` 时目标值每帧降 **−0.025**（`Location.as:3155-3163`、`3240-3248`）。
   ⇒ 墙的明暗边界在**移动时是"滑"过去的**，从不瞬跳。
3. **无二值化**：`gameA = floor((1-gv)*255)` 直接吃连续量 `gv`，不存在"整瓦全亮/整瓦全黑"的分档。

RV 的地板/门场这三层**一层都没有**：
- 空间上 10px 子格（`fogSub=4`）且 12.5px σ 的模糊不足以把 10px 台阶抹平；
- 时间上 `computeFov` 一触发就整场重算，`needFov` 由 4px 眼点位移驱动（`1100`），**瞬时跳变**；
- 还有 `cLit==4/0` 的**瓦片级二值分档**（R4）。

### 3.4 门/窗为什么不平滑？—— 六条独立机制

- **R2a 平顶**：门后整片恒为 `doordim`（本机 0.85 ⇒ alpha 38）。模型实测：门后区域**只有 1 个 alpha 取值**，
  单一值占比 **100%**；而同样几何下的开口/窗是 **45–71 个取值**、值域 `[31..101]`（有距离渐变）。
  平顶意味着"门后世界没有明暗层次"，观感是一块**贴纸**；它的边界只剩"在锥内 / 不在锥内"二值。
- **R2b 叶面丢失透射率**：`computeFov` 的墙可见性传播用 `opac>0` 作为"候选"条件（`:1869`），
  于是**任何透光瓦片只要挨着可见地板就被提升为 VISIBLE**（`:1880`），
  `fillFogCache` 的 `t.opac>=1` 判断又不把它当墙（`:2304`）⇒ 它落到地板分支，
  `lit` 的衰减**从未用于叶面自身**。结果：木门/窗在雾层里等于"墙上开了一个无雾的洞"。
  模型：门、窗、纯开口三者的叶面 alpha 都是 `16..29` —— **完全一样**，即"玻璃/木门"在雾里不可见。
- **R2e 快路径丢 `lit`（窗这一半的头号）**：`cLit==4` 就整瓦 `fillLitTile`，alpha 只由 `distFalloff` 决定，
  `lDist1=300` 内直接 0 ⇒ 窗(0.2)/栅格(0.1) 在画面里**整体消失**，只在锥体边缘留一圈 51/26 的环带。
- **R2f 墙/地亮度反向**：门后地板 = 38（RV 射线 + `doordim`），门后墙 = `1-visi` ≈ 204（原生扣了门的 0.8）。
  同一空间里地板比墙亮 160+ 级，落差沿 40px 瓦片线分布；`wallEdgeLight` 只在 `opac<1` 时才去采样地板雾，
  所以没有任何代码弥合它。
- **R2c 缺口径统一**：即使叶面修好，门后区域仍是"从玩家距离衰减"而非"从开口距离衰减"，
  且被 `doordim` 硬钳平（见 R2a）；与相邻的 VISIBLE 瓦片走两套公式，交界在 40px 瓦片线上。
- **R2d 瓦片级二值分档**：`cLit==0` 时整瓦记忆（v0.34.4 的 `flags&240` 只覆盖"`f==VISIBLE` 且角点被半径内遮挡"），
  `cLit==4` 时整瓦全亮 ⇒ 窄缝（窗缝/门缝）在锥体边缘最容易落进这两档，产生 40px 尺度的块状错判。

## 4. 缺陷清单

> 严重度：**S1** 正确性（看穿/看漏几何）；**S2** 观感结构（口径不连续）；**S3** 维护性/一致性。
> "证伪方法"是给实施者用的：如果这一条能被证伪，对应的候选修复就可以降级或撤回。

### F-1（S1）`castRay` 从不检测起点格 ⇒ 起点格一旦不透明，整面墙对射线失效

- **机制**：`castRay` 以 `c0x=floor(ex/TILE), c0y=floor(ey/TILE)` 起步（`:1905-1906`，缓存分支 `:1962-1964`
  用 `cell = c0x + c0y*rayWidth`），**第一步就跨出起点格**，循环里累减的全是"跨过的格子"（`:1965-1995`）；
  循环结束后只额外处理**目标格**（`:2028-2037`）。全程**没有任何一处**读起点格的 `opac`。
  （原生 `Location.lighting()` 同样从 `_loc16_=1` 起步、同样不采样眼点格 —— 但原生只影响**显示亮度**，
  而 RV 用它决定 `fov[]` 三态与单位遮罩，所以同一个豁免在 RV 里升级成"几何是否正确"的问题。）
- **后果**：起点格若 `opac>=1`，该格对**所有**射线透明；整面墙（1–2 瓦片厚）被"打穿"，
  墙后的房间/走廊按正常距离衰减被点亮，单位遮罩（`currentSight`）也同步点亮（同一份 `castRay`）。
- **为什么这是"回归"而不是"一直如此"（关键判读）**：v0.34.3 之前 RV 的起点是 `(gg.X, gg.Y − gg.scY*0.75)`
  —— 它**恒在碰撞盒内**（`scY*0.75 < scY`），和原生的 `(gg.X + storona*12, gg.Y1 + stayY*0.247)`
  一样安全。v0.34.3 为了让"阴影视线与画面眼部一致"改成读显示眼点（`:1767-1786`），
  **却没有同时恢复"起点必须在体内"这个前提** ⇒ 起点豁免从"安全的设计"变成"可触发的漏洞"。
  这条改动本身是对的（用户当时抱怨的就是视线与眼部不一致），缺的是配套护栏。
- **量化（模型，`tools/door-fov-20261104`，§6.D）**：
  | 姿态（盒顶正好贴墙面） | 眼点 | 起点格 opac | 墙后（row<6）被点亮的格 | 雾 alpha 与"起点格也计入"反事实差 ≥40 的像素 |
  |---|---|---|---|---|
  | 站立（盒 50×70，Y=350） | (842.1, 287.6) → 行 7 | **0.0（自由）** | **0** | **0.0%** |
  | 坐姿（盒 50×35，Y=315） | (842.1, 252.6) → 行 6 | **1.0（墙内）** | **47** | **23.2%** |
- **证伪方法**：探针里让玩家 `sit(true)` 贴墙、并打印 `floor(eye/TILE)` 的 `opac`；若该格恒为 0，则本条的触发路径不成立
  （但缺陷本身仍成立：`castRay` 的豁免是代码事实）。

### F-2（S1）眼点合理性未校验：站立安全、**坐姿**越界

- **机制**：v0.34.3 起眼点取自显示对象 `vis.osn.body.head.morda.eye` 的世界坐标（`:1767-1786`），代码**不校验**它是否落在
  可站立/可透光的格子里。
- **玩家身体盒**：`UnitPlayer` 构造时 `id = "littlepip"` 并立即 `getXmlParam()`（`UnitPlayer.as:329-351`），
  所以拿到的是 `AllData.as:20-24` 的 `<phis sX='50' sY='70'/>` ⇒ `stayX=50, stayY=70`
  ⇒ 站立盒 `[X−25, X+25] × [Y−70, Y]`。
  （**注意：不是 40×40**。`Unit.as:102-108` 的 40/40 只是"没读到 XML 时的默认值"，玩家不走这条。）
- **实测眼点**（v0.34.3 探针 `checks-06/evidence/result.json`，6 个姿态）：
  相对脚点 `eyeX−gg.X ∈ [−22.1, +22.1]`、`eyeY−gg.Y ∈ [−52.8, −62.4]`（`old=(X, Y−0.75·scY)`，`scY=70`）。
  - **站立**：盒顶在 `Y−70` ⇒ 眼点在盒顶**下方 7.6–17.2px**、盒左右**内侧 2.9px**
    （**余量只有 2.85px 横向 / 7.6px 纵向**，非常薄）⇒ 该姿态恒在盒内 ⇒ 恒在自由格。
  - **但余量这么薄，构型一变就出界**：同一轮的**性能夹具曾捕获到 `(X+48.7, Y−9.6)` 的眼点（横向越盒 23.7px）**。
    该姿态未记录（可能是跳跃/冲刺/击退/躺卧/特殊动画中的某一帧），但它证明"站立/移动中眼点跑到盒外"**不是纯理论**。
    ⇒ 不能只靠"站立安全"下结论，必须有 C-Eye-1 的护栏。
  - **坐姿**：`sitX = stayX = 50`、`sitY = stayY/2 = 35`（`Unit.as:1037-1044`），`sit(true)` 把 `scX/scY` 改成
    `50×35`（`2519-2524`）⇒ 盒顶降到 `Y−35`，**同样的头部高度就在盒顶上方 17.8–27.4px**；
    同时矮盒让玩家能再贴近墙 35px。两者叠加 ⇒ 眼点落进墙瓦片 17.8–27.4px。
  - **自动坐姿**：`Unit.as:2108-2117`——玩家向上移动（`isUp`）且**站着不动**、上方格非实体、下方格实体且 `zForm==0` 时，
    游戏会把脚点吸附到 `_loc3_.phY1`（下方墙的顶沿）并 **`sit(true)`**。也就是说"在墙沿/台阶边停住"这个动作本身就会进坐姿。
  - 其它可能让眼点落进 `opac>0` 格子的合法路径：**水/`Area.tileop` 区域**（玩家能站进去，`tileOpac>0`）、
    **幽灵墙 `phis==3`**（`Spell.gwall`，玩家可穿过）、`loc.sky` 房间（`collisionAll` 直接返回 false）、
    脚本传送/被单位挤压。
- **证伪方法**：探针 `sit(true)` 后读 `gg.scY` 与眼点所在格 `opac`；若 `scY` 未变 35 或眼点仍在自由格，则坐姿路径不成立。

### F-2b（S3，需实测）眼点顶部与"半墙"叠加的观感混淆

- `zForm>0` 的墙 `opac=0`（`Tile.as:281-297`）—— 它对光照**完全透明**，只在视觉上变矮。
  玩家贴这种墙"能看到墙后"是**原生设计**，不是缺陷；但如果用户反馈的"墙"其实是这类半墙，则 F-1 不是主因。
- 判别方法：诊断日志里打印眼点所在格与周围 3×3 的 `(opac, phis, zForm)`；`opac==0 && zForm>0` 即半墙。

### F-3（S2）墙可见性传播把透光瓦片提升为 FOV_VISIBLE ⇒ 门/窗叶面丢失透射率

- **机制**：`:1859-1894`。候选条件 `if(t.opac <= 0) continue`（`:1869`）意味着 **`opac>0` 即候选**（墙、木门、窗、栅格全在内）；
  命中条件只看**邻格**是 `VISIBLE && opac<=0`（`:1880`）。⇒ 挨着可见地板/墙的透光瓦片被无条件提升。
- **后果**：
  1. 叶面自身 `lit`（木门 0.2 / 窗 0.8）**没有被任何分支使用**，叶面按 VISIBLE 走地板口径；
  2. 叶面在 `fillFogCache` 里因为 `opac<1` 不走 `fillWallTile`，于是**既不是墙也不是门景**，成"亮洞"；
  3. 与叶面相邻的墙瓦片，其角值来自 `explorationLight(邻格)`（`:2614`/`:300`），
     会"借"到叶面被衰减过的 `visi` ⇒ 墙沿开口被压暗一圈（模型：门场景左邻墙 `42..223` vs 开口场景 `20..200`）。
- **量化**：模型里门/窗/开口三者叶面 alpha **都是 16–29**（无差别）；反事实（只对 `opac>=1` 传播）后
  门叶变成 `[38]`（正常门景），墙—门边界落差从 ~200 降到 ~64。
- **证伪方法**：真机截图里把一扇木门关着看：如果门板与周围墙的雾度连续、门板明显比门后暗，则本缺陷不成立。

### F-4（S2）门景区域是"平顶"，没有内部渐变

- **机制**：`recalcTile` 的 lit 分支 `br = lit*falloff; if(br<floorF) br=floorF;`（`:2437-2446`），
  `doorView` 时 `floorF = cfgDoorDim`。木门 `opac=0.8` ⇒ `lit=0.2` ⇒ `lit*falloff ≤ 0.2 < 0.85`
  ⇒ **`br ≡ 0.85`**，与距离、与开口几何都无关。
- **量化**：模型门后区域原始 alpha `[38..38]`、**单一值占比 100%**；对照：开口 `[31..101]`/57 种取值、
  窗 `[31..101]`/45 种、宽开口 `[31..101]`/71 种（§6 表 A）。
- **后果**：门后的房间失去明暗层次，观感是"一块统一亮度的贴纸"；它的边界只剩二值几何边界，
  仅由 12.5px σ 的模糊软化。墙的阴影边界同处二值，但**内部有渐变**，所以看上去"厚"而不是"薄"。
- **证伪方法**：把 `doordim` 临时调到 0.6（= `dim`），若"不平滑感"显著减轻，则本缺陷被确证为主因之一。

### F-4b（S2）门后"地板很亮、墙很暗"——两套亮度源在同一条视线上打架

- **机制**：门后空间的**地板**走 RV 射线 + `doordim`（本机 alpha **38**）；
  同一空间的**墙**走原生 `tile.visi`（`explorationLight:300-309`），而原生 `visi` 是**会扣掉门 opac 的**：
  透过 0.8 的门 → `t_visi≈0.2` → 墙显示 alpha `≈ (1-0.2)*255 = 204`。
- **后果**：透过一扇木门看过去，画面是"**地板几乎全亮（38）、墙几乎全黑（204）**"——
  同一空间里地板与墙的亮度差了 **>160 级**，而这个落差正好沿 40px 瓦片线分布。
  这是"门窗的边界看着别扭"里最容易被眼睛抓住的一条：**不是边界在哪里的问题，而是边界两侧亮度反了**。
- **佐证**：`wallEdgeLight:2676-2688` 在 current 模式下、**只有当 `tile.opac<1` 时**才去采样地板雾；
  墙瓦片自己的轮廓走原生光分支 ⇒ **没有任何代码去弥合这道缝**。
- **证伪方法**：裁一张"关着的木门 + 门后可见一堵墙"的截图；若门后的墙比门后的地板明显更暗（而不是更亮），则本条确证。

### F-5（S2，**窗这一半的头号机制**）`fillLitTile` 快路径完全丢弃 `lit`

- **机制**：`fillFogCache:2363-2366` 只要 `f==FOV_VISIBLE && cLit==4` 就整瓦走 `fillLitTile`；
  而 `fillLitTile:2486-2513` 的 alpha **只由 `distFalloff` 决定**，没有 `lit` 项：
  `f = distFalloff(d²); if(f<dimF) f=dimF; a = (1-f)*255`。
  再叠加 `2487-2493` 的"远角在 `lDist1=300` 内就整块 `fillRect(0)`"。
- **后果**：`lit=0.8` 的窗、`lit=0.9` 的栅格（`grate` 0.1）在 300px 内**和"没有障碍"完全一样**（alpha 0），
  衰减只在 300px 外的 `dimF` 环带里体现 ⇒ 窗/栅格在画面里"几乎不存在"，其存在只剩**锥体边缘一圈**
  （51 级 / 26 级）的 40px 环带。这正是"窗提供的视野边界看不出是个窗、只剩下一条边"的机制。
- **附带的死字段事实**：`computeFov` 计算并写入的 `this.br[]` 与 `this.litArr[]`（`:1837-1838`、`1887-1888`）
  在**整个文件里从未被读取**（只有初始化与写入，共 6 处）——注释里说的"连续亮度（原版渐变）"实际上没有消费者，
  显示层的亮度全部由 `fillFogCache` 自己重新算。修 C-Ap-4 时不要假设这两个字段是"现成的连续场"。
- **证伪方法**：受控探针里在同一位置比较"开着的窗"与"拆掉玻璃（opac=0）"两种情况；若两者雾场逐像素相同，则本条确证。

### F-6（S3）目标格 `opac` 被扣两遍

- **机制**：`while` 循环在**步入目标格之后**才检查退出条件，因此目标格的 `opac` 已在循环内被累减一次（`:1994`）；
  循环退出后又**再采样一次**并累减（`:2028-2037`）。
- **后果**：落在透光格上的射线亮度被低估：
  木门 0.2→0（`leaked` 兜底 0.05）、窗 0.8→0.6（**恰好落在 `litmin=0.6` 边界**）、水 `wopac` 同理。
  对 `fov[]` 分类、`litArr`、以及任何用 `lit` 的下游都有影响（目前因 F-3 把叶面提升为 VISIBLE 而被部分掩盖）。
- **证伪方法**：单元级断言：`castRay(eye → 门瓦片子格)` 期望 `1-opac`，实测会得到 `max(0, 1-2*opac)` 或 0.05。

### F-7（S3）`MASK_LIT_A` 固定 140 与可调 `dim` 不同源

- **机制**：单位遮罩阈值是硬编码 `140`（`:155`），而雾下限由 `dim` 推导（`dimA=round((1-dim)*255)`）。
  本机 `dim=0.6 → dimA=102 < 140`；历史上默认 `dim=0.35 → dimA=166 > 140`。
  `recalcTile:2458` 的 `logicalA` 又用 `max(logicalBrightness, doorView?floorF:0.35)` 与 140 比较。
- **后果**：`dim` 调到 0.55 以上时，"远处的暗部"与"记忆区"在**单位遮罩**语义上会翻转到可见侧，
  而血条/描边/可抓取判定都吃这个阈值 ⇒ 可能出现"看不清但敌人/血条显形"的错位。
- **说明**：当前 `dim=0.6` 下并没有直接表现为本次两条反馈，但它是"为什么用户调参后感觉更怪"的潜在放大器。

### F-8（S3）子格射线无半径守卫 ⇒ 探索溢出

- **机制**：`recalcTile` 对瓦片内**所有**子格无条件 `castRay`（`:2407-2412`），没有 `locDist2` 判断
  （对比 `fillWallTile` 前的角点采样有 `dx*dx+dy*dy <= d2max` 的判断，`:2341`）。
  凡 `lit>0.0001` 的子格都会写 `seenSub`（`:2421-2425`）。
- **后果**：视野半径外的"被照亮"子格被记成"曾见"（探索/记忆边界外扩），并让 `fillMemoryTile` 少走整块快路径。

### F-9（S3）`bboxFovCount` 把"被传播点亮的墙瓦片"算作可见

- **机制**：`bboxFovCount`（`:3321-3338`）只判 `fov != FOV_NONE`；而墙瓦片会被 F-3 的传播点亮成 `FOV_VISIBLE`。
  `unitBBox` 又向四周外扩 1 瓦片（`:3290-3293`）。
- **后果**：贴墙敌人的包围盒里"可见瓦片"比例虚高 ⇒ `enemyState` 的 80%/15% 门控更倾向判"全可见"（state 1）。
  `dimTiles` 守卫只挡 `FOV_DIM`，挡不住这种虚高。

## 7. 优化方案

### 7.0 设计原则（先定原则，再谈实现）

1. **单一射线语义**：任何"看得见/看不见"的判定只允许由一套 `castRay` + 一套 alpha 公式产生；
   不允许"墙一套、门一套、叶面又一套"。**口径可以不同（墙/地板确实不同），但必须在交界处数值连续。**
2. **起点必须合法**：视野射线的起点永远不能落在 `opac>0` 的瓦片里；这是几何约束，不是近似。
3. **可回滚**：每个候选都要有配置键或"旧行为开关"，且默认值不改变现有观感除非该候选被判定为缺陷修复。
4. **不新增每帧常驻成本**：优先在 `computeFov`/`fillFogCache`（只在 `needFov` 帧执行）里做，
   避免进入每帧路径；任何每帧新增必须给可测成本。

### 7.1 P0 —— 正确性（必须修，风险低，收益确定）

#### P0-D 先做诊断，再动刀（强烈建议作为第一批的第一项）

在改任何行为之前，先加一段**默认关闭、`debug=1` 才开**的诊断，用来把"用户到底在什么姿态下看到墙后"从推测变成事实：

```actionscript
// 只在 computeFov 之后、debug=1 时，每 30 帧最多写 1 行
// RVision.log: fovdbg pose=std|sit f=..., eye=(x,y) cell=(cx,cy) opac=.. phis=.. zForm=..
//              ring=[(opac,phis,zForm) x 3x3] leakTiles=<墙后 fov!=NONE 的格数>
```

- 记录：`gg.isSit`（或 `gg.scY`）、眼点、眼点所在格 `(opac, phis, zForm)`、3×3 邻域、以及"玩家所在行的对面（墙后 1–3 格）里 `fov != FOV_NONE` 的格数"。
- 判定：`opac>=1` ⇒ F-1 被触发；`zForm>0 && opac==0` ⇒ 是半墙（原生设计，不是 bug）；`opac` 在 `(0,1)` ⇒ 水/tileop 起点豁免。
- 成本：只在 `debug=1` 生效，默认零开销。

**为什么先做**：站立贴墙已被模型排除（§F-1 表），所以"复现姿态"决定后续改法。如果诊断显示眼点从不进墙，那么用户看到的更可能是
F-2b 半墙、或者 §9.2 里的单位门控（历史 v0.24.6 的同类问题），可以省下一整批改动。

#### C-Eye-1 眼点合法性钳制（修 F-1 + F-2）

**目标**：`computeFov` 拿到的眼点永远位于 `opac==0` 的瓦片内；不改变"视线从眼部发出"的既有语义（v0.34.3 的成果）。

**改动点**：`RealisticVisionMod.as:1767-1786`（`playerVisionEye`）之后、`computeFov:1795` 之前，新增 `sanitizeEye`。
关键点：**必须用"当前姿态"的盒子**（`gg.X1/X2/Y1/Y`），因为 `scY` 会随坐姿变成 35：

```actionscript
/** v0.34.9：把显示用眼点夹回"合法的观察点"——不仅要在碰撞盒内，
 *  还必须落在 opac==0 的瓦片里（castRay 从不检测起点格，见 RV-DESIGN-20261104 §F-1）。
 *  只在 FOV 重算时调用（O(1)~O(5) 次 getTile），不进每帧路径。
 *  注意：坐姿时 gg.scY=35（sitY=stayY/2），X1/X2/Y1 已由游戏按当前姿态更新，
 *  所以这里直接读 gg.X1/X2/Y1/Y 而不是重算盒子。 */
private function sanitizeEye(gg:UnitPlayer, eye:Point):Point
{
   var cx:int = int(eye.x / Tile.tileX), cy:int = int(eye.y / Tile.tileY);
   if(this.eyeCellFree(cx,cy)) return eye;                        // 最常见：一次查询
   // 1) 沿"眼点 -> 盒中心"的连线回退，逐点测试（最多 6 点，步长 4px）
   var mx:Number = gg.X, my:Number = gg.Y - gg.scY*0.5;
   for(var k:int = 1; k <= 6; k++)
   {
      var t:Number = k/7;
      var px:Number = eye.x + (mx-eye.x)*t, py:Number = eye.y + (my-eye.y)*t;
      if(this.eyeCellFree(int(px/Tile.tileX),int(py/Tile.tileY))) return new Point(px,py);
   }
   // 2) 夹回当前姿态的碰撞盒内（内缩 1px，避免浮点落在边界上）
   var bx:Number = Math.max(gg.X1 + 1, Math.min(gg.X2 - 1, eye.x));
   var by:Number = Math.max(gg.Y1 + 1, Math.min(gg.Y    - 1, eye.y));
   if(this.eyeCellFree(int(bx/Tile.tileX),int(by/Tile.tileY))) return new Point(bx,by);
   // 3) 最后退到盒中心偏上（v0.34.3 之前的 body 近似点）
   return new Point(mx, my);
}
private function eyeCellFree(cx:int,cy:int):Boolean
{
   if(cx < 0 || cy < 0 || cx >= this.spaceX || cy >= this.spaceY) return false;
   return this.tileOpac(this.curLoc,this.curLoc.getTile(cx,cy)) <= 0;
}
```

调用点：`onFrameInner:1094` 与 `computeFov:1795` 的 `playerVisionEye` 结果统一过一遍（**只在一处做**，
建议放进 `computeFov` 并把结果写回 `this.eyeX/eyeY`，同时把 `onFrameInner` 的 `moved` 判定也改用钳制后的点，
以免"眼点在墙里抖"持续触发重算）。

**预期效果**：模型已证：起点格不透明时泄漏 47 格 / 23.2% 像素差 → 经过钳制后眼点必在自由格 → 0 格 / 0%。
**代价**：常见路径 1 次 `getTile`；退化路径最多 6+1 次。**无每帧成本**（只在 `needFov` 帧）。
**风险**：坐姿时钳制会把眼点从"盒顶上方 ~20px"拉回到盒内（即 `Y−34` 附近），视野中心下移 ≈20px，
观感会比现在"贴地平视"一些。这是**正确方向**（否则就是穿墙），但需要在真机上确认不出现"坐姿视野突然变低"的不适。
**回滚**：`eye_clamp=0` 关闭（默认 1）。

#### C-Eye-2 起点格兜底（修 F-1 的"最后防线"）

**目标**：即使 C-Eye-1 因未知姿态（变身/坐姿/载具/特殊动画）失效，也**不可能**出现"整面墙透明"。

**改动点**：`castRay:1952-1964` 之后，把起点格计入：

```actionscript
// v0.34.9：起点格也必须参与遮挡。C-Eye-1 已经保证正常情况下不会命中这里；
// 命中即说明眼点非法——此时宁可整屏变暗（可恢复），也不能穿透墙体。
var op0:Number = cached ? opacity[c0x + c0y*this.rayWidth] : this.tileOpac(loc,loc.getTile(c0x,c0y));
if(op0 >= 1) return -1;
if(op0 > 0) { leaked = true; lit -= op0; }
```

**预期效果**：极端姿态下退化为"看不见"而非"看穿"；同时兜住"站在水/tileop 区域里时该格衰减被跳过"这一条。
**代价**：每条射线多 1 次数组读取（缓存分支）/1 次 `getTile`（非缓存分支）。按 v0.34.5 的射线量级，
缓存分支是主流路径，成本 ~O(1) 次数组访问/射线；需在 §9.3 用 A/A 带核对（预期落在噪声带内）。
**风险**：若 C-Eye-1 有漏判，可能出现"贴墙时周围全黑一瞬"。**必须与 C-Eye-1 同批上线**，并保留诊断日志。
另需注意：C-Eye-2 的 `lit -= op0` 会让"站在水房里"的视野**变暗**（因为现在才真正扣了 0.2–0.75）。
这是**修正**而不是回退，但用户可能习惯了过去偏亮的观感 → 建议作为可见变化写进发布说明。
**回滚**：`eye_guard=0`。

#### C-Ap-1 墙可见性传播只作用于实心墙（修 F-3）

**目标**：透光瓦片（门/窗/栅格/水）的透射率不再被传播逻辑吞掉。

**改动点**：`computeFov:1869`，把候选条件从 `opac>0` 收紧为 `opac>=1`：

```actionscript
- if(t.opac <= 0) { continue; }
+ if(t.opac < 1) { continue; }   // 透光瓦片按自身 lit 归类，不接受"邻居可见"提升
```

**预期效果**（模型反事实）：门叶 16..29 → `[38]`；窗叶保留少量雾；叶面与墙的落差 ~200 → ~64。
**代价**：零。**风险**：透光瓦片将**不再被点亮**（它们改为按自身 `lit` 归类）。
若某类瓦片（例如半透"假墙" `fake`/`t_ghost`）过去依赖这条传播产生亮度，会变暗 → 需要 §9.2 的"门/窗/栅格/水/电墙"覆盖测试。
**回滚**：`opac_promote=0/1`（1=旧行为）。

#### C-Ray-1 目标格只扣一次（修 F-6）

**改动点**：`castRay:2028-2037`，加一个"目标格是否已在循环内被采样"的判定：

```actionscript
// 循环在步入目标格后才退出，此时该格 opac 已在 1994 行累减过一次。
var sampledInLoop:Boolean = (c1x == tx && c1y == ty && guard > 0);
if(!sampledInLoop)
{
   op = cached ? this.rayOpac[tx+ty*this.rayWidth] : this.tileOpac(loc,loc.getTile(tx,ty));
   if(op >= 1) return -1;

```

（非缓存分支同理；注意"目标格 == 起点格"时 `guard==0`，必须仍然扣一次。）

**预期效果**：木门后 `lit` 0.05 → 0.2；窗 0.6 → 0.8；水瓦片同理。
**风险**：会改变 `fov[]` 在三态边界上的归类（`litmin=0.6` 附近），属于**行为变化**，
必须按 §9 做"三态分布对照"（期望：仅三类瓦片附近变化，几何轮廓不变）。
**回滚**：`ray_target_once=0`。

### 7.2 P1 —— 口径统一（"不平滑"的主修）

> P1 的目标不是"把门画得跟墙一样亮"，而是：**让门/窗区域与墙共享同一套连续场**，
> 使"边界"变成一条有内部支撑的边界，而不是三块不同贴纸的交界。

#### C-Ap-2 透光瓦片改走"表面口径"（修 F-3 的后半 + 表 B 的落差）

**目标**：门板/玻璃/栅格自身的 alpha 与相邻墙**同族、连续**。

**改动点**：`fillFogCache:2304` 之后、`2309` 之前插入新分支：

```actionscript
if(t.opac > 0)            // 透光表面：门板/玻璃/栅格（实心墙已在上面处理）
{
   this.fillTranslucentTile(loc,tx,ty,t.opac);
   continue;
}
```

`fillTranslucentTile` 与 `fillWallTile` 同构（四角双线性），但角值改为"**透过该瓦片后的可见度**"：

```actionscript
/** 透光瓦片的表面亮度 = 原生角点亮度 × 透射率，再取门景下限。
 *  与 fillWallTile 共享同一角点场 ⇒ 与相邻墙在共享边上数值连续。 */
private function transCornerAlpha(loc:Location,x:int,y:int,opac:Number):Number
{
   if(x >= this.spaceX || y >= this.spaceY) return 255;
   var gv:Number = this.explorationLight(loc,x,y);       // 原生 visi（:300）
   gv *= (1 - opac);                                     // 透射率
   var cur:Number = this.memCur[x + y*this.spaceX];
   var a:Number = 255 - gv*255*(1-cur+cur*this.cfgDim);
   return Math.max(a, Math.round((1-this.cfgDoorDim)*255));   // 门景下限，与 doordim 语义一致
}
```

**预期效果**：门板从"无雾亮洞"变成"有雾且有渐变"，与墙同属一条 40px 角点场；
`doordim` 成为**下限**而不是"整片的绝对值"。
**代价**：每个透光瓦片多 4 次 `explorationLight`（原本地板分支已有 ~4 次角点射线，量级同级）。
**风险**：`doordim=0.85` 时下限 38 仍远亮于记忆 102，门板会**比墙亮**（这是用户当前偏好）。
若希望"门板比墙暗"，需要用户把 `doordim` 调低（如 0.4 → 下限 153）。→ 见 §10 决策 B。
**回滚**：`aperture_surface=0`。

#### C-Ap-3 门景：平顶 → 径向渐变（修 F-4，观感主修）

**目标**：门后区域获得**距离渐变**，使"看穿门"与"看得见多远"一致；并在视野边缘与记忆区连续。

**改动点**：`recalcTile:2427-2446` 的 lit 分支，当 `doorView` 时不再用常量下限，而用**渐变后的有效下限**：

```actionscript
if(doorView)
{
   // v0.35：门景不再是常量平顶。
   //  近端（脚下, falloff=1）用 doordim；远端（视野边缘, falloff=0）降到 dim，
   //  于是门后区域有渐变，且在 locDist2 处与记忆区同值 ⇒ 不出现"贴纸边"。
   var fade:Number = 1 - falloff;                  // 0=近, 1=视野边缘
   var floorEff:Number = this.cfgDoorDim
      - (this.cfgDoorDim - this.cfgDim) * Math.min(1, fade * this.cfgDoorGrade);
   var b2:Number = lit * falloff;                  // 原式的 lit×falloff 项，保留
   br = b2 < floorEff ? floorEff : b2;
   logicalBrightness = b2;                         // 单位遮罩仍按未抬高的原始亮度判
}
```

其中 `cfgDoorGrade` 为新配置键 `doorgrade`，默认 **1.0**：
- `1.0`：门后亮度从 `doordim`（近）平滑降到 `dim`（视野边缘）；
- `0.0`：**完全等于现状**（`floorEff ≡ doordim`）→ 一行回滚口。

> 实现提示：`recalcTile` 目前把 `distFalloff` 内联在 `br = lit * this.distFalloff(sdx*sdx+sdy*sdy)` 里（`:2439`），
> 需要先取出 `var fo:Number = this.distFalloff(sdx*sdx + sdy*sdy);`，再分别用于 `fade` 与 `b2`。
> `fillLitTile` 那条路径（`lit` 被丢弃、`fillRect(0)` 快路径）**不会**走 `recalcTile`，
> 所以门景渐变只影响 `f==FOV_DIM` 的瓦片；窗/栅格要靠 C-Ap-4。

**预期效果**（模型可直接复算）：门后区域从"1 个取值"变成连续谱（预期 30–60 个取值），
且光锥边缘的内外两侧值差从 `doordim−dim = 0.25`（64 级）收窄到"随距离线性收敛到 0"。
**代价**：零额外射线；每子格多 2 次乘加（只在门景瓦片的子格上，且只在 `needFov` 帧）。
**风险**：**这是观感变化**——门后远处会变暗。用户若更喜欢"亮而平"的门景，把 `doorgrade` 调小即可。
需要在真机上让用户当面比较 `doorgrade ∈ {0, 0.5, 1}` 三档（§10 决策 A）。
**回滚**：`doorgrade=0`。

#### C-Ap-4 快速路径带上 `lit` 因子（修 F-5 —— **P1 首项，窗/栅格半边的主修**）

**目标**：让"整瓦全亮"的快路径不再把 `lit<1` 的透光场合当成空气。

**改动点**（三处，一起做才有意义）：

1. `fillFogCache:2363-2366`：把瓦片级 `lit` 传进去（**不要用死字段 `litArr`**，它虽然被写但从没被读；
   用 `computeFov` 里同一位置已经算出的值，或在这里补一次瓦片中心的 `castRay` 并缓存）。
2. `fillLitTile:2486-2513`：把 `f = distFalloff(d²)` 改成 `f = distFalloff(d²) * litF`；
   `litF` 由调用方传入，`litF==1` 时行为与今天**逐位相同**（默认 1 → 可配置开关）。
3. `fillLitTile:2487-2493` 的"整块 fillRect(0)"：改为 `(1-litF)*255` 的常数填充（同样在 `litF==1` 时等价于 0）。

```actionscript
// fillFogCache 调用处
var litF:Number = this.cfgLitFastPath ? Math.min(1, this.tileLit[i]) : 1;
if(f == FOV_VISIBLE && cLit == 4) this.fillLitTile(tx,ty,bx,by,dimF,cs,litF);
```

**预期效果**（模型可直接复算）：窗后 300px 内不再是 alpha 0，而是 `(1-0.8)*255 = 51` 的"有玻璃"基底，
并在锥内保留距离渐变；栅格（0.1）为 26。与相邻墙的 0..223 渐变**落在同一量级**，边界不再是"无 → 有"的突变。
**代价**：`tileLit` 每 FOV 帧一次数组；`fillLitTile` 每子格多 1 次乘法。
**风险**：会让所有"透过窗/栅格/水面看到的区域"**变暗一层**（用户可能觉得"看得不如以前清楚"）。
这是把"不该看见的亮度"收回来，但属于明显的观感变化 → 必须与用户当面确认（§10 决策 B 的延伸）。
**回滚**：`lit_fastpath=0`（默认 1）。

#### C-Ap-5 角值补偿：不要让墙"借"到被衰减的亮度、也不要让墙与地板各说各话（修 F-3 的第三点 + F-4b）

**改动点 A**：`refreshWallField:2614`（以及 `sceneRefreshWallFieldFast:1712`）里的
`gv = this.explorationLight(loc,tx,ty)`，当该格是透光瓦片时做透射率补偿：

```actionscript
var t2:Tile = loc.getTile(tx,ty);
var gv:Number = this.explorationLight(loc,tx,ty);
if(t2.opac > 0 && t2.opac < 1 && 1-t2.opac > 0.15) gv = Math.min(1, gv / (1 - t2.opac));
```

**改动点 B（F-4b 的正解）**：让"门后空间的墙"与"门后空间的地板"用**同一个亮度源**。
两种做法，二选一：
- **B1（推荐，改动小）**：`fillWallTile` 在 `current` 模式下，若该墙瓦片处于**任一 FOV_DIM 邻域的锥内**
  （即它的 8 邻居里有 `f==FOV_DIM`），则改用"地板场同源的采样"——直接取 `fogRaw`（模糊前）在该瓦片外侧的 alpha，
  与 `wallEdgeLight:2676-2683` 已经做过的事情一致，只是把它从"仅透光瓦片"扩展到"门景锥内的墙"。
- **B2（更彻底，改动大）**：墙与地板统一走 `visi` 或统一走 RV 射线（二选一），不再混用。
  代价是墙的原生质感会变（原生 40px 双线性是"墙平滑"的来源），**不建议**在本轮做。

**预期效果**：门后"地板 38 / 墙 204"的反向落差被拉平到同一量级（B1 下墙会取到 30–50 附近）。
**风险**：B1 会让门后的墙变亮（更像"透过门看过去"），但会削弱墙体的立体感；需要在真机上用"门后有一堵墙"的场景单独确认。
**回滚**：`door_wall_merge=0`。

### 7.3 P2 —— 时间平滑（需拍板，视觉延迟取舍）

#### C-Time-1 门/窗区域的一阶低通

**问题**：墙边界靠原生 `visi` 的 +0.1/−0.025 每帧迟滞"滑"过去；地板/门场每次 `computeFov` 瞬跳。

**候选实现（两种，二选一或分档）**：
- **T-a 子格 alpha 低通**：新增 `Vector.<Number>` 长度 `spaceX*fogSub × spaceY*fogSub` 的插值场（小房间 48×25×4²=19.2k 项；大图 240×125×16=480k 项 → **只对小图启用**），
  每帧 `cur += clamp(target-cur, -step, +step)`，`step = cfgFadeStep`（0.1）；
- **T-b 只在"门景瓦片"上做**：只对 `f==FOV_DIM` 的瓦片做时间插值，成本与门/窗数量成正比（通常 <20 瓦片）。

**代价**：T-a 内存 4–8MB/大图（不可接受）→ 大图必须用 T-b；T-b 的观感收益局限于门后。
**风险**：引入 6–10 帧延迟（与历史 C-Fov-1 同类取舍，2026-11-03 曾因"视觉延迟"撤回降频建议）→ **必须用户拍板**。
**回滚**：`door_fade=0`（默认 0，即不启用）。

### 9.3 真机与性能口径（按 `remains-release-gate` 的适度验证）

- **必须**：同场景 A/B（旧字节 vs 新字节）各 2 轮 + **同字节 A/A** 一轮，报告 RV 计时差与 A/A 噪声带；

- **不要**：把训练室（30fps 锁帧、负载轻）的差值当作玩家机器的收益。
- **要**：记录 `RVision.log` 的 `init ok vX` 版本行、`tick` 计数、以及 P0-D 的 `fovdbg` 行。
- **真机视觉验收**（用户当面）：①**按用户的复现姿态**（坐/蹲/贴墙/水房）确认不再看穿；②门/窗/墙同屏时"边界粗细"观感一致；
  ③`doorgrade` 三档比较；④水房/栅格房不出现全黑或全亮。

## 10. 需要用户拍板的分支

| # | 决策 | 选项与后果 |
|---|---|---|
| **A** | 门景要不要保留"平顶" | ①`doorgrade=1`：门后有距离渐变，最像墙，但远处的门后房间会变暗；②`doorgrade=0`：现状（统一亮度贴纸感）；③0.3–0.5 折中。**推荐 ①，先看三档再定** |
| **B** | 门板应比墙亮还是暗 | 当前 `doordim=0.85`（下限 alpha 38）比记忆区（102）亮很多，意味着"关着的木门在雾里几乎是通透的"。若把 `doordim` 降到 0.4（alpha 153）门板会明显变暗、门后仍可辨。**推荐先保持 0.85**，只修口径（C-Ap-2/3），避免一次改两件事 |
| **B2** | 窗/栅格要不要"变暗一层" | C-Ap-4 会让透过窗(0.2)/栅格(0.1)看到的区域从 alpha 0 变成 51/26。这是把丢失的透射率还回来，但用户可能觉得"看得不如以前清楚"。**推荐做**，并当面比较开/关 `lit_fastpath` |
| **C** | 是否接受时间平滑 | C-Time-1 会让门/窗边界"滑"过去（更像墙），代价是最多 ~10 帧延迟。历史上曾因"视觉延迟"撤回降频建议，所以**默认不做**，等真机观感反馈 |
| **D** | 批次 1 是否单独部署 | 建议**单独部署**：它只修正确性（不漏光、叶面有雾），不引入观感取舍，可独立回滚 |
| **E** | 目标格二次扣减是"有意的"吗 | 原生**根本不扣目标格**（`Location.as:3210-3229`），RV 扣两遍几乎可以确定是笔误（循环内一次 + 循环后一次，见 F-6）。**推荐按缺陷修**；若担心改变手感，可先用配置键默认关，等真机对照后再开 |

### D. 与历史结论、其它调查的关系

- **v0.34.4-door-smooth**（2026-11-02）修的是"门景平顶覆盖被遮挡子格"与"窄缝四角漏检"。
  本方案指出**它没有触及**：①门后区域在 `doordim=0.85` 下仍是单值平顶（F-4）；
  ②透光叶面被传播提升为 FOV_VISIBLE（F-3）；③射线起点格豁免（F-1）。
  ⇒ 用户"仍不平滑 + 贴墙看穿"的反馈与这些未触部分一致。
- **原生侧只读调查**（`native-fov`，2026-11-04）：[2026-11-04-native-light-and-door-fov.md](../knowledge/investigations/2026-11-04-native-light-and-door-fov.md)
  给出本方案 §3.3 的原生证据链（`lightBmp` 49×28、1 样本/瓦片角、`scale=40`、`smoothing=true`、无额外 blur；
  `visi` 只升不降且运行时 639 房间里仅 2 间 `retDark`；原生**没有**门景下限，`doordim` 是 RV 自造；
  原生射线同样从 `i=1` 起步故眼点格不采样，但目标角点格一般也不扣——RV 反而扣了两次，见 F-6）。
  该文件还独立复现了 F-6（目标格扣两遍），与本轮结论互相印证。
- **不重复已否决路线**：本方案**不**采用"降频/节流 `computeFov`"（C-Fov-1，仍待拍板）、
  **不**采用"撤遮罩/跳过绘制"类诊断候选（历史上被判定为不是修复）。
- **性能纪律**：沿用 2026-11-04 clip-pad 的结论——训练室量级下的计时差异多数落在同字节 A/A 噪声带（±5%），
  本方案的候选都声明为**正确性/观感修复**，不作帧率收益声明；C-Eye-2 的每条射线 +1 次数组读取需实测确认在噪声带内。
- **本轮自我更正记录**：初稿曾依据 `Unit.as:102-108` 的默认值 `stayX/stayY=40` 得出"站立贴墙眼点越界 2.1px"。
  复核 `UnitPlayer.as:329-351`（`id="littlepip"` + `getXmlParam()`）与 `AllData.as:20-24`（`sX=50 sY=70`）后确认
  玩家盒子是 **50×70**、站立时眼点恒在盒内，该推断**作废**，F-2 已按坐姿重写。保留此条以便后续不再重复走同一弯路。
