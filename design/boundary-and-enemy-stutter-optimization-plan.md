## 1. 现象与问题收紧

用户在实测中提供了两项极其关键、具有突破性的定性线索：

1. **现象一（开火卡顿收紧）**：
   过去的“开火导致卡顿”结论收紧为：**“存在正在渲染的阴影边界时，开火会导致卡顿”**。
   - 对应现象：在开阔的纯亮区开火，帧率平稳，无明显卡顿；但只要弹道经过明暗交界的阴影边界，或者屏幕中正在动态重绘阴影边界时，开火就会剧烈掉帧或产生周期性顿挫。
2. **现象二（敌人活动偶发卡顿）**：
   **“单独的敌人活动似乎也会造成卡顿（无论敌人多少），但不能稳定复现”**。
   - 对应现象：屏幕中哪怕只有 1 个敌人，并没有大群敌人堆叠，该敌人在做某些活动时也会突发卡顿；并且不是每帧必卡，表现为偶发、不稳定复现的长帧尖峰。

这两项线索直接推翻了“敌人数线性累积瓶颈”或“开火纯原生粒子过载”的粗略假设，将排查切口精确锁定在**“阴影边界的特定渲染机制”**以及**“单实体触发的临界状态/事件级开销”**上。

## 2. 深度源码调查与机制还原

### 2.1 为什么开阔亮区开火不卡，而穿过阴影边界会卡？

通过对 `RealisticVisionMod.as` 弹体遮罩全链路的追踪，发现了两套截然不同的运行分支：

#### (1) 开阔亮区（纯亮）的无损极速路径
源码位置：`RealisticVisionMod.as:4210–4214`
```actionscript
// Leave fully lit native visuals untouched.
if(raster.fullyLit)
{
   if(record != null) this.releaseWorldVisual(visual, record);
   return;
}
```
- 当玩家在开阔亮区开火时，弹体（`Bullet` / `PhisBullet` / `SmartBullet`）包围盒覆盖的所有瓦片均为纯亮。
- 在 `refreshMask`（3551行）中，`matches == totx * toty` 命中，标记 `raster.fullyLit = true`。
- 弹体**完全不挂载遮罩 Shape，不分配 BitmapData，不计算 BlurFilter，不开启 `cacheAsBitmap`**。
- 原生以极高效率直接渲染，因此玩家在开阔地无论如何扫射都完全不卡。同理，纯暗区命中 `raster.fullyDark` 挂空 Shape，也不产生重度合成开销。

#### (2) 穿过阴影边界时的重度管线与底层“缓存击穿”
当弹道跨越阴影明暗边界时，`fullyLit` 与 `fullyDark` 同时失效，进入混合软遮罩处理：

1. **瓦片位图高频创建与垃圾激增**：
   子弹飞行速度极快（通常每帧位移 15~40 像素），每一帧都会跨入新的瓦片坐标区间 `[x0, y0, x1, y1]`，生成不同的签名键 `(x0<<24)|(y0<<16)|(x1<<8)|y1`。这导致字典 `worldMasks` 中频繁分配新的 `BitmapData`（`m2d`、`m2e`、`maskInput`），产生大量的短暂驻留对象与内存碎片。
2. **逐瓦片模糊滤镜与双通道变换**：
   在 `refreshMask`（3595行、3651行）中：
   ```actionscript
   bdb.applyFilter(bd, bd.rect, this.fogPoint, blur); // CPU 卷积模糊
   soft.paletteMap(soft, soft.rect, ...);              // 调色板通道重映射
   soft.threshold(eligible, eligible.rect, ...);       // 二值门控截断
   ```
   每一块新涉及的混合瓦片都会在 CPU 上跑完整的模糊卷积与像素映射。
3. **最致命的底层杀手：动态子弹的 `cacheAsBitmap` 缓存击穿**：
   源码位置：`RealisticVisionMod.as:4282–4285`
   ```actionscript
   if(shape.cacheAsBitmap !== !drawDark) shape.cacheAsBitmap = !drawDark; // true
   var useCache:Boolean = drawDark ? record.cache : true;
   if(visual.cacheAsBitmap !== useCache) visual.cacheAsBitmap = useCache; // true
   if(visual.mask !== shape) visual.mask = shape;
   ```
   - 在 Adobe AIR / Flash 渲染引擎底层，为显示对象启用 `cacheAsBitmap = true` 并挂载 `cacheAsBitmap = true` 的遮罩，会为两者分别分配一张离屏位图表面（Offscreen Surface），再进行硬件/软件 Alpha 混合。
   - **但是，子弹每帧都在剧烈旋转（`rotation`）、移动与伸缩**！
   - 对于不断变换旋转角度和坐标的矢量显示对象，**开启 `cacheAsBitmap` 恰恰是性能灾难**：Flash 内部的位图缓存每帧失效（Invalidate），迫使引擎每一帧都重新在 CPU 上将子弹的矢量几何栅格化为新位图，并重新上传纹理表面！
   - 当一秒射出 10~20 发高射速子弹（如轻机枪 LMG），且多颗子弹同时处于边界时，每一颗子弹都在同时进行：**瓦片分配 → BlurFilter 卷积 → 矢量子弹重新栅格化 → 纹理上传 → 双层 Alpha 遮罩离屏合成**！直接造成渲染管道的严重拥塞。

#### (3) “正在渲染的阴影边界”引发的恶性共振
为什么用户特别指出是“**存在正在渲染的阴影边界**”？
- 如果眼点绝对静止，视野场是静态的，`fovVersion` 不变。
- 但如果玩家在跑动中开火、或者开火微后坐/受击位移导致眼点变动超过 `cfgMotionStep`（4px）：
  `computeFov` 被触发（`fillFogCache` 单次耗时约 12ms），同时 `this.fovVersion++`。
- 一旦 `fovVersion` 递增，所有 raster 的 `rec.lastFov` 与 `coverageFov` **瞬间全部失效**！
- 视野场重算（12ms）+ 所有弹道跨界遮罩强制重新检查生成 + 旋转子弹位图缓存每帧击穿，多重开销在同一帧内集中爆发，瞬间产生 40ms~100ms+ 的严重顿挫！

### 2.2 为什么单独的敌人活动也会卡顿？且敌人数无关、无法稳定复现？

针对“单独 1 个敌人”、“敌人数无关”、“偶发且不稳定复现”三大特征，我们在代码中捕获到了三处隐蔽根因：

#### 根因 1：`enemyState` 逻辑漏洞导致的临界状态剧烈二值翻转（Flip-Flop）
在 `RealisticVisionMod.as:3355–3363` 的遮罩门控代码中，存在一处严重的逻辑缺陷：
```actionscript
if(mixed && this.cfgEnemyFast == 1)
{
   var gateRatio:Number = litWeight / tileCount;
   if(gateRatio >= 0.8 && dimTiles == 0) return 1; // ≥80% 判全可见
   if(gateRatio <= 0.15) return 0;                  // ≤15% 判全隐
   // 【严重缺陷】：当 0.15 < gateRatio < 0.8 时，代码没有 return 2！
}
return !mixed && combined == 2 ? 1 : 0;
```
- **代码陷阱**：当敌人处于 15%~80% 之间的临界过渡区时，由于遗漏了 `return 2`，代码跌落到底部执行 `return !mixed && combined==2 ? 1 : 0`。因为 `mixed == true`，所以 `!mixed` 恒为 `false`，导致代码**直接返回了 0（全隐）**！
- **抖动与卡顿爆发机理**：
  - 当一个敌人在阴影边界附近徘徊、或者仅仅在原地待机播放呼吸、微晃动画时：
  - 如果它的包围盒在某几帧恰好在 80% 边界两侧微幅波动（例如 79% ↔ 81%）：
    - **79% 帧**：判定为 `st = 0`（全隐），触发 `hideUnit(u)`，将 `vis.visible = false`、`hpbar.visible = false`，摘除遮罩；
    - **81% 帧**：判定为 `st = 1`（全可见），触发 `showUnit(u)`。**`showUnit` 内部立即调用了原版高开销方法 `u.visDetails()`**（见下方分析），同时启动 5 帧的渐入 Alpha 逻辑（`fadeCount = 5`）；
    - **下一帧若跌回 79%**：立即再次进入 `st = 0`，强杀渐入并清空；
    - **再下一帧若升回 80%**：再次触发 `showUnit(u)` 与 `visDetails()`！
- **`visDetails()` 的原生开销**：
  查阅反编译代码 `fe.unit.Unit.as:2979`：`visDetails()` 会遍历检查单位的血条、装甲、Hero 状态，并对 `hpbar.bar`、`hpbar.armor` 执行 `gotoAndStop(...)` 帧跳转！这种在 Flash 原生显示树上的频繁帧跳转与显隐切换，足以让单帧出现数毫秒的渲染卡顿。
- **为什么不稳定复现**：因为只有当敌人的站位、朝向与动画帧恰好卡在 80% 这个细窄的临界线上时才会触发剧烈翻转；一旦敌人走开，翻转立即停止。

#### 根因 2：单敌进入软遮罩（`state = 2`）时庞大骨骼树的每帧缓存重绘
在非极速模式，或者某些特殊边界情况下，敌人一旦进入 `state = 2`（部分可见）：
源码位置：`RealisticVisionMod.as:3426`
```actionscript
if(!u.vis.cacheAsBitmap) u.vis.cacheAsBitmap = true;
if(u.vis.mask !== s2) u.vis.mask = s2;
if(!s2.cacheAsBitmap) s2.cacheAsBitmap = true;
```
- 敌人的身体（`u.vis`）是一个层级极其庞大、包含多层嵌套的矢量骨骼元件（`osn.body.head.morda.eye...`）。
- 敌人在行走或攻击时，骨骼元件的每一帧都在播放 Flash 动画（内部元件位移/旋转）。
- 当对一个正在播放复杂骨骼动画的 MovieClip 设置 `cacheAsBitmap = true` 时，Flash **每一帧都必须将整棵骨骼树重新栅格化一遍**！
- 此时哪怕场上只有 **1 个敌人**，只要它身上挂着软遮罩且在移动，单这一个敌人的骨骼栅格化与两层遮罩合成就能吃满单帧 CPU，导致明显的掉帧！

#### 根因 3：单敌活动引发的链式外部效应与全局 GC 尖峰
- **敌人开火/投弹**：敌方单位发射的子弹（`Bullet`）、手雷同样被挂载到 `loc.firstObj`，在 `applyWorldVisuals` 中与玩家子弹走完全相同的路径。如果敌人在暗处开火且弹道擦过阴影边界，瞬间引发前述的弹体遮罩卡顿。
- **敌人攻击命中玩家**：敌人如果击中玩家，玩家产生的击退/硬直微位移会使 `playerVisionEye` 跳动超过 4px，瞬间引发全屏视野场重算（`fillFogCache` 12ms+）。
- **AIR 引擎的全局 GC 停顿（GC Spike）**：
  由于弹道与敌人遮罩频繁分配 `new BitmapData(...)`，累积到 Adobe AIR 的内部 GC 阈值时，引擎会强制触发一次全堆 Mark & Sweep 垃圾回收，耗时 50ms~300ms。由于 GC 爆发取决于累计分配总量，与当前屏幕敌人数无关，因此在单敌活动时也会随机爆发。

## 3. 系统优化方案

基于上述调查结论，制定针对性强、改动风险低、画质与性能兼顾的三大优化支柱：

```

                    │               RealisticVision 边界与活动优化方案             │
                    └──────────────────────────────┬──────────────────────────────┘
                                                   │
         ┌─────────────────────────────────────────┼────────────────────────────────────────┐
         │                                         │                                        │
         ▼                                         ▼                                        ▼
┌─────────────────────────┐               ┌─────────────────────────┐              ┌─────────────────────────┐
│ 支柱一：弹体遮罩轻量化   │               │ 支柱二：敌人状态防抖    │              │ 支柱三：动态 FOV 迟滞   │
│ (消除开火跨边界卡顿)    │               │ (消除单敌偶发卡顿)      │              │ (阻断全屏重算恶性级联)  │
```

### 方案支柱一：弹体跨边界软遮罩轻量化（针对现象一）

#### 措施 C-Bul-1：高速弹体禁用 `cacheAsBitmap`（核心首要优化，预计收益极大）
- **实现原理**：
  在 `applyWorldVisual`（4284行）中，识别当前显示对象是否属于高速瞬态弹体（`kind == 2`，即 `Bullet` / `PhisBullet` / `SmartBullet`）。
  对高速弹体：**强制保持 `visual.cacheAsBitmap = false`**！
  遮罩 Shape 仅使用普通矢量裁剪（不开启 `shape.cacheAsBitmap`），或者仅让遮罩 Shape 自身持缓存，绝不让旋转的弹体自身开启位图缓存。
- **预期收益**：
  彻底消除 Flash 引擎每帧因为子弹位移和旋转而打碎位图缓存、强制重新栅格化矢量弹体的庞大开销。多发子弹连续跨界时的渲染顿挫预计可消除 60%~80%。

#### 措施 C-Bul-2：收紧弹体支持区（Support Area）并做瓦片量化复用
- **实现原理**：
  当前 `refreshMask` 使用统一的外扩宏 `MASK_PAD_X = 2`、`MASK_PAD_TOP = 2`，这对大体型单位合理，但对于尺寸仅数像素的子弹而言过于宽大（额外圈入了 4~5 个瓦片）。
  针对弹体（或小尺寸瞬态物体），将外扩量收紧至 1 格瓦片（`PAD = 1`）。同时引入瓦片对齐复用池，多颗处于相邻瓦片的子弹共享同一个只读瓦片遮罩，避免每颗子弹独立申请 `new BitmapData`。

#### 措施 C-Bul-3：极速档（`fx_vision_quality = 0`）弹体快速路径
- **实现原理**：
  在配置为快速档时，弹体在明暗边界不再创建任何遮罩，而是使用极轻量的中心点视野查表（`fxCenterLit`）：在亮区直接原生渲染，进入暗区后直接将弹体 `alpha` 设为 0 或挂载空 Shape，完全消除跨界时的任何滤镜与位图操作。

---

### 方案支柱二：消除敌人边界状态剧烈翻转与骨骼重绘（针对现象二）

#### 措施 C-Ene-1：修复 `enemyState` 逻辑漏洞并引入状态迟滞（Hysteresis 施密特触发器）
- **修复漏项**：
  在 `enemyState`（3360行）中，补齐 `0.15 < gateRatio < 0.8` 时的语义：在此区间内明确返回 `2`（部分可见，挂软遮罩），不再错误跌落返回 `0`。
- **引入双阈值迟滞（施密特触发器）**：
  为了彻底解决敌人在临界线微晃导致的 0 ↔ 1 频繁跳变，引入有状态的迟滞机制：
  - 如果敌人当前处于 **隐藏状态（state = 0）**：
    必须当可见瓦片加权比例达到 **`gateRatio >= 0.85`** 时，才允许跃迁为全可见（state = 1）；
  - 如果敌人当前处于 **全可见状态（state = 1）**：
    必须当可见瓦片加权比例跌破 **`gateRatio <= 0.70`** 时，才允许跌落为隐藏（state = 0）；
  - 中间处于 `0.70 ~ 0.85` 的过渡带时，**保持前一帧的状态不变**（或平滑保持当前遮罩）。
- **预期收益**：
  彻底消除单个敌人在阴影边缘呼吸、走动时每秒数次的状态震荡，阻断伴随状态翻转而爆发的原生显示树重构。

#### 措施 C-Ene-2：限制原生重度方法 `visDetails()` 的调用频次
- **实现原理**：
  在 `showUnit(u)` 中，记录敌人上次调用 `visDetails()` 的帧号以及血量/装甲快照。如果单位的血量与装甲没有发生实质变化，且距离上次调用不足 30 帧，则仅恢复 `visible = true` 与 `prior = 1`，跳过冗余的 `visDetails()` 帧跳转与重新计算。

#### 措施 C-Ene-3：对播放动画的敌人禁用 `cacheAsBitmap`
- **实现原理**：
  在 `applyMask` 中，检查敌人当前是否处于行动/攻击态。对于非静止站桩的敌人，禁止对其身体 `u.vis` 开启 `cacheAsBitmap = true`。避免骨骼动画帧切换将 Flash 内部位图表面打穿。

---

### 方案支柱三：动态视野场（FOV）节流与微位移死区（阻断连锁反应）

#### 措施 C-Fov-1：眼点抖动死区过滤（Eye-jitter Deadzone）
- **实现原理**：
  在 `playerVisionEye` 与 `needFov` 判定处（1069行）：
  `var moved:Boolean = Math.abs(eye.x-this.lastGX)>threshold || Math.abs(eye.y-this.lastGY)>threshold;`
  当前 `threshold` 固定为 4px。但开火的微小后坐力动画、敌人的流弹击中硬直（stagger）往往会造成 4~6px 的微弱眼部抖动。
  在玩家非主动行走（按键无输入）时，将眼点触发阈值提高到 **6px**，或者限制连续两帧之间不得连续触发 `computeFov`（强制至少间隔 1 帧）。
- **预期收益**：
  切断“开火/受击微小震颤 → `computeFov` 耗时 12ms 强制重算 → 全局 raster 失效 → 弹道遮罩强制重绘”的恶性链条。

## 4. 实施阶段与验证计划

为确保改动的绝对安全可控，优化方案按照“**先修逻辑漏洞与免除负收益缓存 → 再做迟滞防抖 → 最后做可选时序节流**”的三阶段推进：

| 阶段 | 编号 | 核心动作 | 影响范围 | 正确性与安全保障 |
|---|---|---|---|---|
| **Phase 1 (首选)** | C-Bul-1 | 弹体禁用 `visual.cacheAsBitmap` | 仅弹体渲染 | 弹体原本就在高速运动，禁用缓存完全无视觉差异，立竿见影 |
| **Phase 1 (首选)** | C-Ene-1 | 修复 `enemyState` 漏项并加入双阈值迟滞（0.70/0.85） | 敌人状态判定 | 消除呼吸抖动导致的翻转，视觉更稳定，无暗区泄漏 |
| **Phase 2 (进阶)** | C-Ene-2 | 节流 `visDetails()` 重复调用 | 敌人显示刷新 | 仅在血量/装甲不变时跳过原生帧刷新，完全保真 |
| **Phase 2 (进阶)** | C-Bul-2 | 弹体支持区收窄至 1 瓦片（`PAD = 1`） | 弹体遮罩范围 | 覆盖子弹羽化所需范围，减少无效瓦片位图分配 |
| **Phase 3 (可选)** | C-Fov-1 | 开火微位移死区过滤与连续重算最小间隔 | FOV 计算频率 | 需验证在贴近墙角时是否会造成轻微阴影滞后 |

### 验证矩阵（基于 ModLoader 隔离测试）：
1. **S0 纯亮区开火基准**：固定眼点开火，记录 RV 耗时与完整帧均值（确认基线流畅度）。
2. **S1 静态边界穿透开火**：眼点静止，弹道横穿阴影边界，比较优化前后：
   - 弹体位图分配次数（`new BitmapData`）；
   - 完整帧 P95 与 >50ms 卡顿帧数。
3. **S2 动态重绘边界穿透开火**：玩家走动同时弹道穿过边界，验证 C-Bul-1 与 C-Fov-1 联合切断恶性共振的效果。
4. **S3 单敌临界线待机测试**：放置 1 个敌人在 80% 边界处待机，监测 180 帧内的：
   - `st` 状态翻转次数（优化前预计高达数十次，优化后降至 0~1 次）；
   - `visDetails()` 调用次数与最大单帧耗时。
5. **S4 纯单敌移动测试**：单个敌人在阴影边界走动，验证骨骼动画禁用 `cacheAsBitmap` 后的平稳性。

## 5. 总结与后续行动建议

本次调查精确解答了用户提出的两个疑难问题：
1. **“存在正在渲染的阴影边界时，开火会导致卡顿”** 的根本原因，在于**跨边界高速旋转弹体在 `cacheAsBitmap` 机制下的每帧位图缓存击穿重绘**，以及**动态 FOV 重算与全遮罩失效的叠加共振**；
2. **“单独敌人活动也会偶发卡顿”** 的根本原因，在于 **`enemyState` 漏项导致 80% 临界线附近的剧烈二值翻转（Flip-Flop）与 `visDetails()` 重度刷新**，以及**带骨骼动画敌人在挂载软遮罩时整树重栅格化的单帧峰值**。

**推荐后续行动**：
首先实施 **Phase 1（C-Bul-1 弹体禁用 `cacheAsBitmap` + C-Ene-1 敌人状态迟滞防抖）**。这两项改动代码量极小、风险极低、完全保真，但直接击中上述两大现象的底层核心，预期将带来显著的卡顿消除效果。
